## 2. 研究问题

论文研究如何测试会在多轮对话中调用有状态工具的 LLM，而不把工具使用简化成孤立的单步 API 选择。重点包括：工具前置状态和隐式依赖、用户追问、信息不足、等价但不同的执行轨迹、不可触发的危险状态，以及工具说明被扰动后的鲁棒性。

## 3. 被测试的智能体类型

- 带函数调用能力的对话式工具智能体；
- 在手机风格的联系人、短信、提醒、设置、位置等状态环境中执行任务；
- 同时测试闭源和开源 LLM；
- 允许多轮用户—智能体交互和多个工具调用；
- 不涉及浏览器视觉、多智能体协作或长期跨会话记忆。

## 4. 测试或评估方法

ToolSandbox 用“执行上下文”在每一步保存世界状态和消息总线，使任意轨迹都可被回放和检查。测试 oracle 不是固定的唯一工具序列，而是：

- **里程碑 DAG**：必须达到的中间或最终状态/消息节点；只要求满足偏序关系，允许合理的替代路径；
- **雷区 DAG**：一旦满足即表示出现不允许的状态或操作；
- **轨迹映射与相似度**：把执行快照按时间和拓扑约束映射到里程碑，使用精确匹配、ROUGE-L、AST 级工具调用比较等相似度；
- **最终得分**：综合里程碑覆盖；触发雷区时可归零。

因此评测同时覆盖结果、过程、顺序和不良副作用，避免只比对一条“标准答案轨迹”。

## 5. 数据集、环境或基准

- 34 个高难度场景模板，组合成 1,032 条被评测轨迹；
- 每个场景平均约 13.9 轮、3.8 个工具；
- 约 44% 的工具具有状态依赖；
- 场景类别包括单工具、多工具、单轮/多轮用户交互、状态依赖、名称规范化和信息不足；
- 作者估计约 85% 场景至少包含一种显著挑战；
- 环境状态可在如飞行模式、蜂窝网络、Wi-Fi、低电量、位置服务等条件下改变工具可用性和结果。

## 6. 评价指标

- 基于动态里程碑的轨迹得分 `[0,1]`；
- 各场景类别的平均分；
- 不同工具扰动下的相对退化；
- 用户模拟器的幻觉率与指令遵循错误率；
- 论文未把经济成本和端到端延迟作为主指标。

## 7. 实验设计

- 比较 GPT-4o、Claude 3 Opus 等闭源模型与多种开源模型；
- 以 GPT-4o 作为用户模拟器，并通过“知识边界”提示及少样本示例约束其只能依据用户可知信息回应；
- 人工标注 1,032 条用户模拟轨迹中的错误，验证提示改进；
- 对工具集合做增强和扰动：加入无关工具、打乱工具名称、工具描述、参数描述或参数类型；
- 单独报告状态依赖、多轮、信息不足等场景的表现；
- 开源实现保存逐步上下文，支持按快照检查 guardrail。

## 8. 主要发现

- GPT-4o 的总体平均分约 73.0，为主表最佳；Claude 3 Opus 约 69.2；最佳开源设置约 31.4，显示当时工具闭环能力有明显差距。
- 用户模拟器如果只使用一般提示，会把不可知信息编入回答或偏离用户目标；加入知识边界和演示后，人工标注的幻觉率从 12.4% 降到 6.97%，指令遵循错误从 6.20% 降到 0.77%。
- 状态依赖场景对模型困难，且并行函数调用可能引入竞态或忽略隐式先决条件；这说明“能选对工具”不等于“能在当前状态下安全执行”。
- 增加干扰工具或扰动工具元数据会显著改变表现，揭示模型对名称、描述和参数 schema 的脆弱依赖。
- 动态里程碑比固定轨迹更公平：它允许不同但正确的工具顺序，同时能对关键顺序、未完成里程碑和雷区副作用施加约束。

## 9. 局限性

- 为每个场景编写里程碑、相似度和雷区需要人工工程，扩展成本高；
- 用户模拟器仍有错误，且同一模型家族作为模拟器和被测对象可能引入相关偏差；
- 环境没有完整覆盖身份认证、敏感写操作确认、撤销与权限升级等生产控制；
- 未覆盖后台守护进程、外部中断和异步事件；
- 一些真实外部 API 难以长期稳定复现，论文建议缓存但不能消除语义陈旧；
- 场景数量有限，不能代表开放世界工具生态；
- 未系统报告随机重复、成本和延迟分布。

## 10. 可复现性信息

- 代码、场景、工具、执行上下文和评分器公开；
- 论文描述了用户模拟器提示、模型比较和扰动类型；
- 可执行世界状态及消息总线使失败轨迹可回放；
- 复现应锁定仓库提交、模型快照、并行工具调用设置、随机种子和 API 缓存；
- 闭源模型更新和外部工具依赖仍会造成长期漂移。

## 11. 与“智能体测试”研究的关系

ToolSandbox 给出了轨迹级 oracle 的工程范式：正确性不是一条精确动作序列，而是一组必要里程碑、偏序关系和不得触发的状态。它也说明测试环境必须把工具前置条件、状态演化和用户模拟器纳入测试对象；否则基准只测“API 名称匹配”，没有测智能体。

## 12. 可借鉴的工程实现

1. 为业务场景定义 milestone DAG 与 forbidden-state DAG；
2. 每次工具调用前后记录不可变状态快照、消息、参数、返回、异常和父 span；
3. 为不同字段配置精确、集合、数值容差、字符串或 AST 相似度；
4. 建立工具 schema 变异测试：重命名、描述删减、类型边界、无关工具和工具版本更新；
5. 把用户模拟器的知识边界变成断言，并以人工小样本定期校准；
6. 测试并行调用时的竞态、幂等性和状态前置条件；
7. 雷区应覆盖越权写入、重复扣费、隐私泄露和不可逆副作用。

## 14. 可以支持综述中的结论

- 工具智能体测试需要有状态、交互式环境；
- 轨迹 oracle 应允许等价路径，但约束关键偏序和危险状态；
- 工具 schema 是需要做变异和回归测试的接口契约；
- 用户模拟器是测量系统的一部分，必须量化其误差；
- 状态依赖与并发会带来普通 LLM 静态评测没有的故障；
- 轨迹级确定性评分可减少 LLM judge 的主观性，但构建成本更高。
