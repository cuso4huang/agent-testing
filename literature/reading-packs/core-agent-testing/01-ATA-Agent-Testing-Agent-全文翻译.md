## 摘要

LLM Agent 正越来越多地被部署，用于借助工具进行规划、检索和写作；然而，对它们的评估仍然依赖静态基准和小规模人工研究。我们提出 Agent-Testing Agent（ATA）：一种元 Agent，它将静态代码分析、开发者问询、文献挖掘和由角色驱动的对抗性测试生成结合起来，并依据评审反馈动态调整测试难度。每段对话均由 LLM-as-a-Judge（LAAJ，LLM 评审器）依照量表评分，并用于引导后续测试，使其聚焦于 Agent 最薄弱的能力。

在旅行规划 Agent 和 Wikipedia 写作 Agent 上，ATA 所揭示的失败比专家标注者发现的更加多样、更加严重，同时在严重程度判断上与人工相符；它可以在 20-30 分钟内完成测试，而由十名标注者参与的一轮测试则需要数天。移除代码分析和 Web 搜索后，测试结果的方差和失准程度均会上升，这凸显了以证据为基础生成测试的重要性。ATA 会为开发者同时输出量化指标和定性 bug 报告。我们发布了完整的开源实现。[^1]

**图 1：** ATA 与被测 Agent（AUT）之间的一次示例交互，顶部显示测试详情。ATA 假设 AUT 可能不擅长处理相互冲突或无法满足的约束，因此生成了一个提出不可能要求的棘手角色。AUT 不知道自己正在与另一个 Agent 对话，并成功解释了该请求为何无法完成（见第 3.2 节）。

## 1 引言

经过指令微调的大语言模型（LLM）催生了大量 Agent 系统。这些系统把模型调用、外部工具与记忆串联起来，以完成用户目标（Yao et al., 2023, 2022）。然而，当数据分布发生变化、工具返回噪声，或者多个细微约束相互作用时，这些 Agent 经常失败。如何提供稳健且对开发者友好的评估，仍然是一个瓶颈。

目前，研究社区仍然主要依赖静态、人工整理的基准，例如用于行程设计的 TravelPlanner（Xie et al., 2024），以及小规模人工研究。这类评估无法覆盖组合式输入空间；随着系统架构演进，它们会迅速过时；维护成本也很高。

另一条互补的研究路线是使用 LLM 直接评判模型输出，或将其作为多 Agent 评估器的一部分（Zheng et al., 2023; Chen et al., 2025）。这些方法虽然能力强大，但通常预设测试列表已经由人工编写。自动测试生成被用于扩大特定领域的覆盖范围，例如客户支持或事实核查（Arcadinho et al., 2024; Lin et al., 2025; Levi and Kadar, 2025）；但这些方法通常既不会依据目标 Agent 的架构进行推理，也不会根据已经观察到的失败自适应地调整测试。

我们提出 Agent-Testing Agent（ATA）：一个无需任何特定领域标注，即可端到端构造并执行对抗性对话测试的元 Agent。ATA：

1. 静态分析目标 Agent 的代码库；
2. 询问开发者，以获取需求和隐含假设；
3. 以文献和数据集为依据进行检索，找出可能的失败模式；
4. 合成由角色驱动的对话，并利用每次评审分数更新显式后验，从而调整对话难度。

每段对话均使用 LLM-as-a-Judge 量表评估。生成的量化分数和定性观察会引导后续测试，使其进一步聚焦于 Agent 最薄弱的能力。

本文有三项主要贡献：

1. 我们提出一种弱点规划算法。它维护显式的难度后验，并用它在线调整测试生成过程。
2. 我们提供一个完全开源、基于标准 API 构建的评估器。它不需要领域标注，同时提供命令行界面和 Web 界面，可支持面向开发者的快速迭代。
3. 我们给出证据，表明 ATA 能以人工标注一小部分的时间成本，发现比专家标注者更多样、更严重的失败模式。我们还通过量表级汇总，以及移除代码分析和 Web 搜索的消融实验，分析了人工评估与自动评估之间的互补性。

## 2 相关工作

### 2.1 基于大语言模型的评审器

随着 LLM 推理能力和上下文容量的提升，利用其他 Agent 或 LLM 评估 Agent 系统性能的研究取得了显著进展。LLM-as-a-Judge（Zheng et al., 2023）引入 LLM 来评估多个 Agent 如何就伦理困境作出决定；该研究还探讨了同伴压力，以及潜在失准的主持 Agent，如何影响群体的最终结果。

JudgeLRM（Chen et al., 2025）使用人工标注进行监督微调，结合推理能力，并通过带有自适应奖励函数的 GRPO 来判断哪一个回答能够产生最好的下游结果。

### 2.2 Agent 评估数据集

当评审 Agent 获得来自目标领域的人工测试问题时，可以产生有用的洞见。然而，能够充分覆盖样本空间的真实用户问题很难获得。为此，TravelPlanner（Xie et al., 2024）提供了 1,225 个由人工整理的旅行规划任务。每个任务都需要调用模拟真实应用的工具，例如距离矩阵和景点列表，并组合多种现实约束。TravelPlanner 通常用于判断 Agent 是否可以动态考虑真实情况，例如航班取消，并据此生成合理行程。

类似地，CoordinationQA（Agashe et al., 2025）包含 198 道来自 LLM-Coordination 游戏环境的多项选择题。要正确回答这些题目，每个 Agent 都必须推断其他协作 Agent 的意图和能力。

### 2.3 自动测试生成

ALMITA（Arcadinho et al., 2024）提出一个为客户支持 Agent 自动生成评估测试用例的框架。LLM 根据用户意图生成包含 API 调用的流程，构建带噪声的流程图，然后从中采样路径，以模拟用户交互。

FACT-AUDIT（Lin et al., 2025）面向事实核查。它收敛到一个分布 \(q(x\mid\Theta)\)，该分布突出 LLM 在现实世界理解方面的局限，并采样能够对这些弱点施压的问题。

Levi 和 Kadar（2025）通过从高层系统提示中构建策略图来自动评估策略遵循情况。与本文提出的 ATA 不同，上述方法都不会通过分析 Agent 的内部代码库和特定架构来确定测试依据，也不会借助 Web 搜索获取知识，更没有与人工评估进行广泛比较。

## 3 方法

Agent-Testing Agent（ATA）包含两个主要阶段：

1. **弱点规划（Weakness Planning）**：构建有关目标 Agent 可能在何处、以何种方式失败的理论。
2. **对抗测试（Adversarial Testing）**：在并行线程中执行自适应对话，以探测这些弱点。

除非另有说明，每个组件都是一次由 GPT-4.1 mini 支持的 Agent 调用，并会向共享状态写入结果。

### 3.1 弱点规划

ATA 的弱点规划阶段负责构建有关 Agent 可能在何处、如何失败的理论。ATA 不依赖固定基准，而是通过与用户交互、结构化检查 Agent 代码库，以及检索领域知识，从零开始建立这套理论。这些组件共同填充一个共享记忆结构。随后，ATA 使用思维链提示，根据共享记忆推断可能的弱点。最终结果是一份经过验证并按优先级排序的失败类型列表，ATA 可以在测试阶段对其进行系统探测，如图 2 所示。

#### 代码与用户依据

流程首先选择被测 Agent（AUT）并初始化全局状态。随后，ATA 静态扫描 AUT 的代码库，构建其逻辑的符号图，并识别容易出错的分支和设计缺口。

ATA 会识别 Agent 节点、状态转移、工具调用、记忆访问模式和异常流程。在此基础上，它构建 Agent 逻辑的符号图：节点是对话状态，边是由工具或条件驱动的状态转移。LLM 解释该图，并描述设计缺口和容易出错的分支，例如不可达节点、错误的重试逻辑，以及对边缘情况缺少回退机制。

与此同时，ATA 会询问用户，以了解 Agent 的用途、领域和评估优先级。

#### 参数收集

接下来，ATA 与用户展开一次每轮只询问一个问题的对话。系统会解释每个回答，以进一步理解 Agent 的领域、用户期望和评估标准。

问题选择由信息增益引导：当 ATA 已经获得全部所需信息，或者用户似乎不再继续参与时，它就停止提问。这样既能减轻用户负担，又能最大化信息量。用户回答会被纳入全局状态，并用于个性化后续推理和生成步骤。

#### Web 搜索

为了获得与相似系统有关的外部知识，ATA 会进入一个文献搜索循环。在每次迭代中，它检索 \(m\) 篇与目标领域有关的学术论文、公共数据集或 bug 报告，总共执行 \(n\) 轮。

ATA 总结这些文档，提取常见失败模式、推荐评估方式等经验，然后利用已经获得的洞见重新表述查询，从而形成一份针对目标 Agent 目标而定制的自举式文献综述。所有发现都会写入中央状态，并在之后用于测试用例合成。

#### 弱点生成

系统把收集到的代码分析、用户输入和 Web 搜索上下文交给思维链提示，生成一份潜在弱点列表。随后将这些弱点呈现给用户，以供验证和修改。

**图 2：** 弱点规划。ATA 分析静态结构 \(C\)，询问 Agent 创建者 \(Q\)，并从学术/搜索语料 \(S\) 中收集证据，生成按优先级排序的失败假设（第 3.1 节）。

### 3.2 ATA 测试线程

确定弱点后，ATA 会为每个弱点启动一个专用执行线程。线程并行运行；每个线程负责生成自适应测试用例、模拟与目标 Agent 的多轮交互，并根据表现更新内部难度模型。

每个线程维护自己的历史和状态，但都可以访问同步系统结果的全局记忆结构。这种并发架构使 ATA 能够高效、独立地评估大量失败模式，并通过批量对抗探测加快系统性弱点的发现。

#### 测试用例生成

对于已经确认的弱点 \(w\)，ATA 会生成用于探测该缺陷的测试角色和用户提示。为了测试不同难度，第一次测试的初始难度设为 \(d_1=5.5\)。

在 1-10 的难度尺度上：

- 1-4 为简单；
- 4-7 为中等；
- 7-10 为困难。

在弱点规划循环中，系统会为每类弱点生成简单、中等和困难测试的示例，并将其加入状态。

ATA 创建的提示组合了：

1. 用户目标；
2. 语言语气，例如含糊或不耐烦；
3. 对话轮数限制；中等难度测试为 8-10 轮，并随难度缩放；
4. 评估标准。

#### 对话执行

ATA 从所生成角色的视角与 AUT 交互，直到达到轮数上限或完成目标。AUT 不知道自己在和另一个 Agent 对话，而会像帮助真实用户一样进行处理。系统记录完整对话。

#### 使用 LAAJ 评估

对话结束后，ATA 使用 LLM-as-a-Judge 框架进行评估。该评审器由生成对话的同一个深度推理 Agent 支持。

测试场景完成后，LAAJ 会接收完整对话记录和相关量表，并依据多个预定义标准进行评估，例如准确性和整体效用。每项标准按 1-5 分评分，LLM 还会根据 Agent 回答的具体方面，为每个分数提供详细理由。

系统随后聚合各项分数，得到 1-10 分的总体表现分数 \(s_k\)。该分数是自适应难度调整的主要指标。

除了数值评分，LAAJ 还会生成完整的文字观察，用于捕捉细微行为模式、回答质量和潜在失败模式。观察 \(o_k\) 被组织成详细分析报告，其中包含对话中的具体例子、已经识别的优缺点，以及关于 Agent 决策过程的上下文洞见，用于指导未来测试。

我们发现，让场景生成器为 LAAJ 提供支持至关重要，因为评审器需要理解每次测试的目的。这也与人工标注相似：人工评估者知道自己所创建测试的上下文，然后才会给对话结果评分。

#### 难度更新与循环

ReAct 框架（Yao et al., 2023, 2022）让 Agent 迭代地产生思考、执行动作、观察结果，然后再思考下一步。受此启发，ATA 使用思维链创建测试角色、执行测试，并根据反馈 \(o_k\) 和分数 \(s_k\) 进行反思，以决定下一轮生成何种测试。

收到前 \(k\) 次测试结果后，系统按以下公式更新难度：

\[
q(d_k,s_k)=\operatorname{clip}
\left[
d_k+\eta\left(2\sigma\left(\frac{s_k-5.5}{2}\right)-1\right),
1,10
\right]
\]

\[
w(s_k)=e^{-\frac{|s_k-5.5|}{3}}
\]

\[
d_{k+1}=
\frac{\sum_{i=1}^{k}w(s_i)\,q(d_i,s_i)}
{\sum_j w(s_j)}
\]

其中，\(\sigma\) 是 logistic 函数，\(\eta=3\)。根据配置，该过程循环三轮，或者在难度收敛时提前停止。每一轮都试图逐渐逼近 Agent 的失败边界：成功后生成更困难的测试，失败后则生成更简单的测试。

系统使用 logistic 函数把单次难度变化映射到 \([-\eta,\eta]\)，使一次测试不会造成过大的难度调整，同时又让较高分数产生实质影响。

远离 5.5 分的测试结果通常可靠性更低：这意味着 AUT 要么没有受到足够压力，无法暴露弱点；要么困难过大，无法形成有价值的对话，因此难以从该测试判断 AUT 的能力。为解决这一问题，系统使用 softmax 更新难度，权重由测试得分与 5.5 的接近程度决定。

**图 3：** 测试执行线程。每个弱点生成一段独立对话，并逐渐提高难度，直到出现失败。ATA 使用评审反馈决定下一次应生成什么提示（第 3.2 节）。

**图 4：** ATA 评估旅行规划 AUT 时自动生成的 15 段对抗性对话的气泡图概览。每个气泡分别显示测试难度和对应的 LAAJ 分数；点击气泡可以打开图 1 所示的完整对话。图中有一半线程仍在执行，稍后会向界面添加剩余气泡。

### 3.3 自适应报告生成

最终报告生成通过一个多阶段流程，聚合所有线程的结果和状态数据。

首先，系统从状态中的已完成测试场景提取“难度-分数”对，并按弱点 ID 和线程进行组织。对于每个弱点，它使用自适应难度算法计算下一难度，并将其作为总体评估分数。

随后，系统计算完整统计信息，包括测试场景总数、总体平均分，以及每个弱点的表现指标。它还会组装丰富上下文，包括测试重点、代码分析结果、参数收集阶段的用户回答，以及弱点明细。

这些上下文被交给负责生成报告的 GPT-4.1 mini Agent。该 Agent 会生成一份结构化报告，其中包括：

- 执行摘要；
- 总体分数；
- 测试摘要；
- 已识别模式；
- 代码修改建议；
- 应优先改进的事项。

报告生成后，AUT 创建者还可以继续向该 Agent 询问测试结果和潜在改进措施。

## 4 自动评估与人工评估相比如何？

本节介绍一项实验：在完全相同的设置下，比较由 LLM 自动完成的两个 Agent 的测试和评估，与人工标注者得到的观察。实验旨在说明使用 ATA 和使用人工测试 Agent 时，各自可能产生的差异与相似性。

### 4.1 被测 Agent

#### 旅行规划 Agent

该 Agent 通过自然对话规划完整旅程，将实时 Web 搜索与预算感知优化结合起来。它支持包含航班、酒店和活动的多目的地行程；会通过追问补充缺失约束；当方案不可行时，会解释其中的权衡。

其实现主要受 Hao et al.（2025）启发。评估量表包含：

1. 约束处理；
2. 沟通质量。

研究场景要求标注者规划一次纽约之旅，并在预算、出发地、饮食需求和航班时间偏好等维度上改变角色设定。

#### Wikipedia 文章写作 Agent

该 Agent 进行多视角 Web 研究，起草结构化提纲，并撰写带引用、分章节的 Wikipedia 风格文章。它以交互方式与用户协作，包括确认主题、批准提纲和多轮修改。

其实现主要受 Shao et al.（2024）启发。评估量表包含：

1. 引用的使用；
2. 完整性；
3. 风格与组织。

研究场景要求标注者撰写英语语言史上某一事件或发展的文章，并改变主题具体程度、引用严格程度和批评性反馈。

### 4.2 实验设置

我们将 ATA 与十名专业标注者进行比较。专业标注者遵循一套结构化协议，包括角色定义、执行对话和依据量表进行评估。

为了公平比较，ATA 被配置为精确复现人工工作流。它使用同一角色模式生成角色，即“态度/性格 + 目标/需求”，并使用完全相同的 Agent 专用量表评判对话。

ATA 在并行线程中执行测试。每个线程系统性地探测一个假设弱点。这一方法旨在用针对每种失败模式的测试深度，补充人工测试的广度。完整的人工标注协议，以及 ATA 为保持一致而采用的配置，见附录。

### 4.3 结果与讨论

我们汇总了每个 Agent 的十名标注者的笔记，将语义相似的问题归为一组，并统计发现每个独特弱点类别的标注者人数。

表 1 和表 2 汇总了人工标注者发现的类别，以及 ATA 对同类问题给出的分数。人工频次表示提到该问题的标注者人数；ATA 分数越高，表示 AUT 在该弱点类别上的表现越强。

聚焦至少一名人工标注者发现的问题，可以观察到四个跨 Agent 主题：

1. **上下文保持与一致性。** 这是人工对旅行规划 Agent 最常见的抱怨，共 7 名标注者提及；在 Wikipedia 写作中也很明显，共 4 人提及。ATA 对两个 Agent 的评价却截然不同：旅行规划 Agent 得分较高，为 7.2/10；Wikipedia Agent 只有 4.3/10。这说明，多页文章写作所需的长上下文推理，比对话式规划中的上下文细节更容易形成实际瓶颈，尽管人工会在两类任务中都注意到上下文问题。
2. **语气与人际互动质量。** 人工经常指出这一问题，旅行规划中有 5 人，Wikipedia 写作中有 3 人；但 ATA 没有发现该维度。这反映出一种已知互补性：人工测试者更擅长捕捉难以事先编码为弱点的语用和人际互动期望。
3. **结构与格式。** 人工认为这一问题对 Wikipedia 写作更突出，有 6 人提及；旅行规划中只有 2 人。ATA 却对 Wikipedia 的结构给出 7.6-7.8 的高分，说明人工使用了更严格的文体标准，例如是否遵循 Wikipedia Manual of Style，而 ATA 的量表没有充分编码这些标准。
4. **性能与速度。** 人工很少提及这一点，旅行规划中 1 人、Wikipedia 写作中 2 人；但 ATA 对 Wikipedia Agent 的惩罚明显更重，得分 2.3/10，而旅行规划 Agent 为 6.9/10。这与文章写作任务更重的检索和起草负载相符。

#### 特定任务模式

人工关注点自然会随领域变化。

在旅行规划中，约束处理/部分约束修正是重要的人工意见，共有 5 名标注者提出；ATA 也确认这方面表现一般，得分为 6.3/10。

在 Wikipedia 写作中，人工主要关注引用/来源，共 8 人，以及事实准确性，共 3 人。ATA 的结果与之呼应：引用为 6.0/10，事实准确性为 6.7/10。

#### 整体比较

总体而言，两种评估路径发现了相互重叠的功能弱点，例如旅行 Agent 的约束处理缺口，以及 Wikipedia Agent 的引用和结构问题。

然而，人工在语言、语气和措辞上的关注比例更高。由于 ATA 本身也是 LLM Agent，它对这些维度的处理更加机械。这种不对称性表明，人工测试在捕捉细微的人际互动质量和语用期望方面仍然有价值，因为这些质量很难事先编码为弱点。

相反，ATA 的线程化设计和自适应测试生成发现了一些人工团队没有系统测试的能力级问题。每个人工标注者往往探索不同角度；ATA 则在每个线程中固定一个弱点，并使用三个角色反复测试，因此可以针对每种失败模式产生更深入的探测，以及更多可直接用于回归测试的用例。

#### 成本与时间

ATA 在 Apple M3 Pro 上完成一次完整运行需要 20-30 分钟。十名标注者的一轮测试，包括安排和执行，则用了十天。这种速度差异对需要快速迭代的 Agent 开发者具有实际意义。更详细的时间和成本分析见附录 D。

#### 按标准汇总的分数

表 3 比较了人工与 ATA 在量表各项标准上的平均分，可以看到两个一致趋势。

第一，在规划标准上，人工对约束满足更加严格，而 ATA 对总体任务成功更加严格。对于旅行 Agent：

- 人工的约束处理分数高于 ATA：4.07 对 3.53，差值为 +0.54；
- ATA 的用户沟通分数高于人工：4.11 对 3.63，差值为 +0.48；
- ATA 的整体效用略低：3.36 对 3.78，差值为 -0.42；
- ATA 的汇总平均分也更低：3.67 对 3.83。

第二，在写作标准上，ATA 对 Wikipedia Agent 的评价整体略微更宽松：

- 引用：3.60 对 3.53，差值 +0.07；
- 完整性：4.00 对 3.70，差值 +0.30；
- 风格/组织：4.10 对 3.80，差值 +0.30；
- 整体效用：3.80 对 3.60，差值 +0.20；
- 汇总平均分：3.87 对 3.66。

#### 解释

这些模式与评价标准的性质一致。在说明性写作中，LLM 评审器更容易奖励结构清楚和覆盖全面，而人工标注者对文体和润色有更严格的要求。

相反，在规划任务中，人工会奖励看似合理的约束处理，而 ATA 会在端到端效用层面更稳定地惩罚“只满足部分约束”的行为。结合 ATA 的速度优势，这些结果指向一种实用工作流：先使用 ATA 进行快速、深度优先的探测和汇总评分，再针对语气、人际互动质量和风格进行定向人工审核。

## 5 消融研究

为了衡量各个推理组件的贡献，我们将完整 ATA 管线与一个消融版本进行比较。消融版 ATA 同时移除了静态代码分析和 Web 搜索，因此只能根据用户提供的目标和浅层角色提示生成弱点。结果见表 1、表 2 和表 3 的第四列。

### 5.1 设计与设置

完整 ATA 使用弱点规划的全部步骤，包括代码层洞见和从文献中获得的压力测试案例。

消融版跳过这些证据收集步骤，在参数收集之后直接进行弱点生成。两个版本使用同一套与量表对齐的评估流程，在 Wikipedia Agent 和旅行 Agent 上执行测试，并为每个弱点线程使用三个角色。

### 5.2 弱点覆盖

完整 ATA 发现了更广泛的弱点，包括：

- 代码层失败，例如在互相冲突的输入下处理约束失败；
- 知识层问题，例如主题覆盖不完整或捏造引用。

消融版 ATA 识别的弱点较少，而且类别更加泛化，例如含糊的沟通或风格问题。

### 5.3 分数分布

两个管线的差异不仅体现在覆盖范围，也体现在评分行为。

#### 方差

消融版 ATA 的分数方差更高。在与人工发现相重叠的弱点上，消融版的 \(\sigma^2=7.15\)，完整 ATA 为 3.23。消融版会同时产生一些非常宽松和过分严厉的评分。这种波动表明，如果缺少证据依据，其测试提示的校准会变差。

#### 相对于人工和完整 ATA 的失准

在表 1 和表 2 中，当人工与完整 ATA 大体一致时，移除代码分析和文献搜索的消融版会明显失准。

- 对 Wikipedia 的上下文保持，消融版过于宽松：8.5/10，而完整 ATA 为 4.3/10。
- 对旅行约束处理，消融版过于严厉：4.1/10，而完整 ATA 为 6.3/10。
- 对 Wikipedia 引用/来源，消融版给出极低的 1.7/10。

最后一点尤其体现了以证据为基础生成测试，对评估研究型标准的重要性。

#### 量表评分比较

表 3 进一步比较了消融版 ATA、完整 ATA 与人工标注者。对几乎所有标准，消融版分数都位于人工平均分和完整 ATA 之间，但这种居中是系统性失准，而非更准确。

例如：

- 在旅行规划中，消融使约束处理分数从 3.53 降至 3.17，反而进一步偏离人工的 4.07。
- 在 Wikipedia 写作中，消融对引用的评分只有 2.24，远低于人工的 3.53 和完整 ATA 的 3.60。

这些差距说明，移除代码分析和文献搜索后，系统会失去对依赖事实依据或结构推理的标准的敏感性。

#### 解释

有趣的是，消融版 ATA 的总体效用偶尔更接近人工，例如旅行任务中，消融版为 3.44，完整 ATA 为 3.36。但这反映的是方差和校准误差，而不是更忠实的评估。

完整 ATA 能够稳定捕捉人工也会惩罚的弱点；消融版则在过度宽松和过分严厉之间摆动。例如，它对 Wikipedia 上下文保持过于宽松，给出 8.5，而完整 ATA 为 4.3；对旅行约束处理又过分严厉，给出 4.1，而完整 ATA 为 6.3。

这些趋势进一步表明，消融版会漂移到泛化评分，而完整 ATA 通过将探测建立在证据驱动的测试生成之上，能够与人工评估取得更强的一致性。

## 6 结论

我们提出 Agent-Testing Agent（ATA）：一个自动对对话式 Agent 进行对抗性评估的元 Agent。

ATA 对被测 Agent 进行静态代码分析，通过交互从开发者处获取缺失的假设，挖掘相关研究和数据集，然后合成由角色驱动的对话，并根据评审反馈自适应地提高难度。对话使用 LLM-as-a-Judge 量表评分，并被汇总为量化指标和定性 bug 报告，可用于回归测试和开发者问题分流。

在旅行规划 Agent 和 Wikipedia 风格文章写作 Agent 上的实验表明，ATA 能发现与人工标注者相重叠的功能弱点，同时还能发现人工没有持续深入测试的能力级失败。

人工更强调语气和人际互动质量；ATA 则更加机械、更加遵循量表地对端到端任务成功施加压力。这两者提供互补的覆盖范围，如表 1、表 2 和表 3 所示。

ATA 完成一次完整评估大约需要 20-30 分钟，而一轮十人标注需要数天进行安排和执行，因此 ATA 可以显著节省迭代时间。

移除代码分析和 Web 搜索后，覆盖范围缩小，校准质量下降：分数方差更高，而且同时偏离完整 ATA 和人工判断。这体现了基于证据生成弱点对于高影响评估的价值。

我们发布了完整方法和可用于生产的开源实现，使研究人员和从业者能够复现实验、根据自身领域修改量表，并以最低开销持续测试自己的 Agent。

未来可以将 ATA 扩展到协作场景，例如多 Agent 协调；增强人工更擅长发现的语用和风格标准；扩大领域适配器和工具模拟器，同时保留 ATA 无需领域标注的特点。

## 局限性

尽管 Agent-Testing Agent（ATA）相比静态基准和纯人工研究具有优势，仍有若干局限值得讨论。

第一，ATA 同时依赖 LLM 生成对抗角色和评判对话结果。这会带来潜在循环性：与被测模型属于同一类别的模型，也为评估提供了支架，因此判断可能偏向 LLM 容易注意到的失败模式，而不是人类用户最在意的失败模式。尽管与人工标注者的比较显示了互补覆盖，但语气、同理心等语用和人际互动质量仍未得到充分捕捉。

第二，ATA 弱点规划框架的通用性，取决于准确的静态代码分析和有效的领域知识检索。消融结果表明，缺少这些组件会降低校准质量；但即使在完整系统中，不完整的代码注释、非常规 Agent 架构或稀缺的公共文献也会降低效果。因此，本方法更适用于文档完善、模块化的 Agent，而不是专有或不透明的系统。

第三，评估循环受到难度调整方式、角色模式和量表粒度等设计选择的限制。尽管迭代调度能够快速收敛，但仍可能遗漏弱点采样空间之外少见却灾难性的失败。类似地，与量表对齐的评分强调端到端任务成功和结构忠实度，却弱化了部署中同样关键的风格细节、延迟和用户满意度。

第四，当前 ATA 针对单 Agent、纯文本交互进行了调优。要扩展到多 Agent 协调、多模态界面，或者带有高延迟和随机 API 的工具链，需要同时调整测试生成和评审标准。这些是有前景的未来方向，但不在当前研究范围内。

最后，我们没有与 ALMITA（Arcadinho et al., 2024）、FACT-AUDIT（Lin et al., 2025）或 GOAT（Pavlova et al., 2025）等相关自动评估框架进行直接量化比较。这些系统面向客户支持、事实核查等特定领域，或依赖不会根据被测 Agent 架构调整的静态基准。ATA 的核心贡献是根据代码库分析和开发者输入来确定测试生成依据；这是一个根本不同的评估范式，如果不针对具体领域重新实现，就无法在共享指标上进行正面对比。

## 附录 C：实验设置详情

### C.1 人工标注设置

十名专业标注者通过 Web Annotator UI 与每个 Agent 交互。对于每个 Agent，标注者完成三个角色测试，并按以下步骤评估：

1. **角色定义。** 标注者首先指定：
   - 角色的对话态度/性格；
   - 该角色在本次会话中的具体目标或需求。
2. **对话。** 标注者从该角色的视角与 Agent 聊天，并尝试在界面规定的轮数预算内实现目标。
3. **评估。** 标注者使用 Agent 专用量表评价对话：
   - 旅行：约束处理、沟通；
   - Wikipedia：引用、完整性、风格/组织。
   
   标注者还需提供自由文本笔记。指南文档另外定义了整体效用尺度，以及在一轮测试中为每个 Agent 准确运行三个角色的分步流程。

提供给人工标注者的界面和文档包含 Agent 描述、测试场景、角色设计指南和详细指标尺度。实验逐字遵循这些材料。量表见附录 A。

### C.2 ATA 如何配置为复现人工协议

我们对 ATA 进行修改，使其使用完全相同的量表和角色结构。

**角色一致。** 对于每个 Agent，ATA 在每个弱点线程中生成三个角色，使用与人工界面相同的角色模式，即“态度/性格 + 目标/需求”。

**量表一致。** ATA 使用与量表对齐的提示评判对话，并复现人工尺度：

- 旅行：约束处理、沟通；
- Wikipedia：引用、完整性、风格/组织。

**线程化测试。** ATA 按弱点拆分测试，每个假设弱点运行一个单独线程。每个线程执行三个角色，并维护自己的观察历史和自适应难度计划。

每个 ATA 线程的行为类似一名单独的人工标注者：

1. 形成假设；
2. 进行对话；
3. 记录观察；
4. 使用观察设计下一次测试。

因此，人工研究与 ATA 都遵循“观察 → 反思 → 探测”的迭代方式。

不同之处是，每名人工标注者会在不同对话中探测 Agent 的不同失败，例如个人关注点和风格期望；ATA 则在一个线程内保持测试对象不变，即固定一个弱点，同时改变探测方式，包括角色、难度和措辞。

这样，ATA 可以针对每种失败模式获得深度，用以补充人工评估的广度。

## 附录 D：成本与资源分析

本节按阶段分析在第 4 节评估设置下运行 ATA 的计算和资金成本。为便于具体说明，我们聚焦于 Wikipedia 写作 Agent。该 Agent 由模型支持，因此其回答会产生调用费用。

### 设置与假设

每次运行覆盖六个弱点；每个弱点进行三次对抗测试，共 18 段对话。

每段对话平均七轮。每轮中，ATA 大约生成 140 个 token，AUT 大约生成 110 个 token。

评审器会使用完整对话记录和量表，约 2,500 个输入 token，并产生约 800 个输出 token。

固定组件包括：

- 静态代码分析；
- 参数收集；
- Web 搜索；
- 弱点规划；
- 报告生成。

### 模型使用

大多数阶段使用 GPT-4.1 mini，包括代码分析、参数收集、Web 搜索、对话生成、评审和报告撰写。

o3 仅被选择性地用于：

1. 全局弱点规划阶段；
2. 每次测试用例生成时的思考循环，共调用 18 次。

这些调用费用更高，但只占总 token 的一小部分。

### Token 统计

一次完整运行中：

- 固定阶段，包括选择、代码分析、参数收集、Web 搜索、弱点规划和报告：约 42,000 个输入 token，约 12,000 个输出 token。
- 对话测试，18 次：约 99,000 个输入 token，约 50,000 个输出 token。
- 评估，18 次量表调用：约 18,000 个输入 token，约 11,000 个输出 token。

合计约 159,000 个输入 token、73,000 个输出 token，总计约 232,000 个 token。

其中约 20,000 个 token，也就是弱点规划和测试用例思考循环，由 o3 处理；其余由 GPT-4.1 mini 处理。

### 成本

按 2025 年 4 月价格：

- GPT-4.1 mini：输入每 1,000 token 0.15 美元，输出每 1,000 token 0.60 美元；
- o3：输入每 1,000 token 1.10 美元，输出每 1,000 token 4.40 美元。

每次运行的混合成本约为 2.50-3.50 美元。

成本会随着弱点数量、测试用例数量和对话轮数线性增长，也取决于 AUT 的输出长度。长篇生成 Agent 的成本会高于输出简短的工具路由 Agent。

### 时间

在 Apple M3 Pro 上，一次运行需要 20-30 分钟：

- 代码分析约 2-3 分钟；
- 检索约 5-7 分钟；
- 执行对话和评审约 12-15 分钟；
- 综合报告约 3-4 分钟。

### 与人工标注比较

基线人工研究使用十名标注者，每人工作 8 小时，即每个 Agent 4 小时；估算工资为每小时 20 美元。因此，每轮评估的人工成本为：

\[
10 \times 8 \times 20 = 1,600\text{ 美元}
\]

该数字尚未包括协调开销。相比之下，ATA 可以在不到半小时内，以每次约 3 美元的成本提供相近覆盖。

### 总结

与人工评估相比，ATA 在时间和资金成本上都实现了数量级下降。虽然绝对成本会随被测 Agent 和输出长度变化，但其扩展规律是可预测的，并近似正比于：

\[
\text{弱点数量} \times \text{测试对话数量}
\]
