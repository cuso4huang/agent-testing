# AgentDoS：程序分析 + 定向灰盒 Fuzzing

**论文**：Jiaqi Luo et al. *Autonomy Comes with Costs: Detecting Denial-of-Service Vulnerabilities Caused by Resource Abusing in LLM-based Agents*. USENIX Security 2026 preprint.

**研究对象**：不是“让 LLM 推理很慢”，而是 Agent 实现层因工具、历史、下载内容或中间数据的无界累积而耗尽内存/磁盘，最终造成服务不可用。

## 为什么传统 Fuzzer 不够

Agent 的输入是有语义的自然语言；仅 bit flip 很难让 LLM 产生可执行且资源消耗高的计划。漏洞还可能跨多轮累积，必须建模资源生命周期。只看是否到达 sink 也不足够：到达了资源操作点，不代表真的产生足以触发 DoS 的消耗。

## AgentDoS 管线

1. **静态程序分析**
   - 定位潜在资源操作符/敏感 sink。
   - 分析数据与控制关系，并对资源生命周期建模。
   - 区分单次调用内的短生命周期资源、会话内长期资源，以及更持久的资源。
2. **语义种子生成**
   - 针对具体功能生成能自然驱动 Agent 到达 sink 的初始请求。
3. **定向调度**
   - 根据种子接近目标、资源消费潜力等反馈优先选择高价值种子。
4. **语义变异**
   - 由 LLM 保持请求可理解、可执行，同时放大次数、数据规模或跨轮累积。
5. **资源型 bug oracle**
   - 不只看 crash；连续监控资源使用和生命周期，判断是否发生异常、无界或足以造成不可用的消耗。

这是一种真正的 **灰盒**：源码分析提供方向，运行时资源信号提供反馈，LLM 负责自然语言输入的结构化变异。

## 结果

- 在 20 个真实 Agent 应用上发现 36 个高风险零日漏洞，影响 16 个应用；论文提交时其中 15 个已获 CVE。
- 人工复核后 36 个报告均为真阳性；以汇总的 38 个已验证漏洞为基准，AgentDoS 达到 100% precision、94.7% recall。
- 对比 AgentFuzz，AgentDoS 找到 36 个，后者仅 3 个。主要差异来自资源生命周期建模、资源消费潜力反馈和语义变异。
- 消融后 recall：无种子生成 81.6%，无调度 65.7%，无变异 42.1%，说明三者都重要，变异影响最大。
- 平均每个 Agent 消耗约 932 万 token；按论文当时 GPT-4.1 价格估算约 44.3 美元，主要时间花在种子变异。

## 两种典型漏洞

- **单轮放大**：让工具在一次任务里重复下载/载入同一大文件，临时对象在调用结束前耗尽内存。
- **跨轮累积**：工具输出和对话历史持续进入会话缓冲区，但未被上下文窗口自然限制，最终无限增长。

## 对通用 Agent 测试框架的启发

- 覆盖反馈可以来自程序事实：sink 距离、数据依赖、资源增量，而不必全靠 LLM judge。
- 状态型测试必须明确 reset 边界：单步、单任务、单会话、跨会话、全局租户。
- 安全预言机应监测斜率和累积量，并设置任务相关预算，而非只设统一超时。
- 防御应组合输入/大小限制、超时、资源配额、去重、生命周期清理和异常告警。

## 局限

- 需要源码，不能直接测试完全封闭的商业 Agent；若能观测延迟或资源侧信道，方法可部分黑盒化。
- 当前重点是内存和磁盘资源；CPU、网络、API 配额与费用耗尽仍可扩展。
- 高 token 成本意味着工程上需要缓存、并行预算与停止准则。
